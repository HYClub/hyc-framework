# 53 · 天赋树（Talent）

## 它是什么

可视化编辑天赋树并在运行期查询的工具。节点之间的连线表示**前置关系**，节点上的"消耗"表示解锁它需要付出多少属性。

| | 行为树 | 天赋树 |
| --- | --- | --- |
| 语义 | 每帧从 Root 往下走一条执行路径 | 静态图，玩家一次性或逐步点亮 |
| 图的形状 | 树 + 可复用子树 | **有向无环图**（一个节点可有多个前置） |
| 数据形态 | Blob（高频游标） | ScriptableObject（低频查询） |
| 打包 | 资产在 Editor 程序集，必须导出 Blob | **资产在 Runtime 程序集，打包即用** |

最后一行是有意为之的行为树教训：`BTTreeAsset` 在 Editor 程序集，打包后一棵树都拿不到，
只能补一条"导出 Blob → 运行期读回"的链路，还落了个"编辑器能跑 ≠ 真机能跑"的坑。
天赋树数据量小、查询不频繁，直接序列化即可，不需要那条链路。

---

## 架构

```
TalentTreeAsset (Runtime, ScriptableObject)
├─ treeId              全局唯一
├─ blackboard[]        属性：key + 指向配置表某一行
├─ nodes[]             节点：id / 名称 / 最高等级 / 消耗[] / 编辑器坐标
└─ links[]             前置关系：from -> to
              │ Build()
              ▼
        TalentTree (Runtime, 只读视图)
              ├─ GetNode / PredecessorsOf / SuccessorsOf
              └─ Validate  (运行期自检：悬空连线 / 环 / 属性引用)
```

**节点没有分类。** 天赋节点不像行为树那样需要 Selector / Sequence / Action 这类功能性区分，
图上每个节点的区别只在于「叫什么名字」和「消耗什么」。加一层玩法语义的枚举（攻击/防御/被动…）
只会限制使用方——所以 `TalentNode` 只有名字、消耗、等级、位置。

**黑板上的属性来自配置表**。`TalentAttribute` 不存数值本身，只存一个 `ConfigRowRef`
（`typeName` + `ConfigId.id`），真正的数据在配置表里取：

```
TalentAttribute.key = "STR"          ← 树内唯一符号，节点消耗引用它
TalentAttribute.sourceRow            ← AttrConfig 的某一行（名字、图标、上限都在那里）
```

天赋树本身不认识"力量"是什么，它只认识 key。

### 为什么宿主是薄壳

行为树编辑器踩过的坑：窗口（`BTGraphWindow`）自己画一部分 chrome、`BTGraphIMGUI` 画画布，
两边各自维护一份布局常量，改一处漏一处。天赋树直接按 BT 的最终形态来——
`TalentTreeWindow` 全文只有「建容器 → `LoadAllTrees` → `OpenTree` → 存盘」四件事，
**一个像素都不画**，界面 100% 由 `TalentGraphIMGUI.DrawGUI()` 负责。

同理，视觉不另起一份 `TalentStyles`，而是 `using HYC.Framework.BT.Editor;` 直接吃
`BTEditorStyles`：圆角盒、圆点、贝塞尔连线、画布底色全部共用一份。
这样"两个编辑器看起来一样"是**结构上的一样**，不是抄一遍数值。

## 用法

**编辑**：菜单 `HYC Framework/Talent/Talent Tree Editor`。

#### 界面布局（与 BT 编辑器逐块对齐）

```
┌──────────────────────────────────────────────────────────────┐
│ 工具栏  File | Edit | Prefs   选中资产 添加节点 自动布局 ...   │ 21px
├────────────┬──────────────────────────────────┬──────────────┤
│ 左栏 210px │            画布                   │ 右栏 262px   │
│ 天赋树资源 │  网格 / 节点卡片 / 贝塞尔连线      │ 天赋树       │
│ ＋新建     │                                   │ 节点属性     │
│ 搜索框     │                          ┌────────┤ 黑板 · 属性  │
│ 列表(手绘  │                          │minimap │ 运行时       │
│  滚动条)   │                          └────────┤ (可折叠)     │
├────────────┴──────────────────────────────────┴──────────────┤
│ 底栏：校验结果 / 节点与连线计数                                │ 88px
└──────────────────────────────────────────────────────────────┘
```

- **工具栏**：`File`（新建 / 保存 / 清空画布）、`Edit`（校验 / 全选 / 复制 / 粘贴 / 删除）、
  `Prefs`（网格 / 吸附 / 左右栏开关 / 连线样式 Hard·Soft·Softer·Direct），
  外加 `选中资产`、`添加节点`、`自动布局`、`适应画布`、`生成代码` 五个常用按钮，右端显示当前树名。
- **左栏**：天赋树资产列表（顶部搜索框过滤，「＋ 新建天赋树」建在 `Assets/TalentTrees/`）。
  当前在编辑的树高亮；**未落盘的临时树**会额外顶一行「(未保存)」，否则列表里找不到它。
  **点任意一行 → 右侧画布立刻重建并自动 `ZoomToFit`**，这是"点了没反应"那个 bug 的修复点。
- **画布**：节点卡片（左侧一条灰色色条——节点不分类型，所有节点同色）、
  标题行、消耗摘要（空则显示"无消耗"）、`最高等级 > 1` 时补一行"每级 · 最高 N 级"。
  底部圆点是输出端口，拖到另一节点即建立前置关系。
- **右栏**：四个可折叠分组 —— `天赋树`（名称 / treeId / 计数）、
  `节点属性`（名称 / 最高等级 / **本地化 Key（只能选，见下）** / 消耗列表 / 只读的前置·后继）、
  `黑板 · 属性`（key 输入框 +「选择配置行 →」按钮；**右键该行可清空绑定**）、
  `运行时`（`TalentTree.Build().Validate()` 自检按钮）。

**本地化 Key 不能手填，且要能看到内容**：它是一个 Unity 原生风格的弹出字段
（`EditorGUI.DropdownButton` + `EditorStyles.popup`），点开走 `LocKeyPickerWindow.OpenDropdown`
——基于 `AdvancedDropdown` 的可搜索 / 层级折叠面板（和 Unity 自己的 "Add Component" 一个皮）。
**按钮主显示是当前语言的翻译内容**（`LocAccess.GetText`），**原始 key 作为暗色副行显示在下方**；
下拉列表里每个 key 也带翻译预览。三种状态：

| 样式 | 含义 |
| --- | --- |
| 灰色禁用 `（未导入本地化数据）` | loc 包没装 / 没导入 Excel，控件禁用 |
| 正常（显示翻译内容） | 已选，且表里查得到这个 key |
| 红色副行 `⚠ 本地化表里没有这个 key` | 已选，但**表里查不到**（拼错 / 表里删了） |

右侧 `×`（或右键按钮）清空。本地化数据没导入时不会乱标红——只在
`LocAccess.GetKeys()` 确实非空时才判定 key 不存在。
- **底栏**：左半是校验结果（✗ N 错误 / ⚠ N 警告 / ✓ 校验通过，下面列出前 2 条明细），
  右半是选中计数、「节点 · 连线 · 缩放」统计与一行快捷键提示。
- **minimap**（右下）：整棵树缩略 + 当前视口框，按住可拖动导航。

#### 操作

| 操作 | 方式 |
| --- | --- |
| 平移 | 中键拖动，或 `Alt` / `Shift` + 左键拖动 |
| 缩放 | 滚轮（以鼠标为中心，0.25–2.5） |
| 框选 | 空白处左键拖动 |
| 移动节点 | 拖动节点卡片 |
| 连线 | 从节点底部圆点拖到目标节点 |
| 右键 | 空白处：添加节点 / 自动布局 / 适应画布 / 重置视图；节点上：添加后继 / 开始连线 / 复制 / 断开全部连线 / 删除 |
| 删除 | `Del` / `Backspace` |
| 复制 | `Ctrl+D`（原地）、`Ctrl+C` / `Ctrl+V`（粘贴到视图中心） |

> 交互原型（可在浏览器里直接点）：[`prototypes/talent-tree-editor.html`](./prototypes/talent-tree-editor.html)。
> 它是外观与操作的参考稿，数据字段以 `TalentTreeAsset.cs` 为准。

**运行期**：

```csharp
using HYC.Framework.Talent;

[SerializeField] private TalentTreeAsset treeAsset;

var tree = TalentTree.Build(treeAsset);

TalentNode node = tree.GetNode(3);
foreach (var cost in node.costs)
{
    // cost.attrKey 去自己的属性系统里查当前值，判断是否够
}
foreach (var pre in tree.PredecessorsOf(node.id))
{
    // 检查前置是否已解锁
}

// 可选：运行期自检
var errors = new List<string>();
if (tree.Validate(errors) > 0) { /* ... */ }
```

**天赋树不说的话**：它不回答"某个玩家有没有解锁这个节点"。那需要玩家的等级、总点数、
已投入点数，是玩法层的事。框架只提供图结构和查询。

## 生成代码 / UI

配置好一棵天赋树后，点工具栏的 **「生成代码」**，能一键产出"运行期逻辑 + UI"三件套，
省掉手写解锁/点亮/可点判定和拖绑定。

生成前先跑 `TalentTreeValidator.Validate`，有 Error 直接拦下并列出。弹出的对话框里填：
**输出目录**（默认 `Assets/HYC/Generated/Talent`）、**类名前缀**（默认取树名清洗）、
**命名空间**（默认由「生成代码命名空间 root」派生：`{root}.Talent`）、以及「仅生成画布选中的节点 / 全部节点」。

### 三件套

| 产物 | 是什么 | 你改哪里 |
| --- | --- | --- |
| `<前缀>TalentController.cs` | **逻辑代码**：同时是 `TalentRuntime`（状态机）和 `ITalentResourceProvider`（资源接口） | `#region USER` 里实现 `GetAvailable` / `Consume`（点数从哪来） |
| `<前缀>TalentUI.cs` | **UI 代码**：`TalentTreeUIBase` 子类，在 `ApplySlot` 里按 `SlotState` 画颜色/文本/特效 | `#region USER` 里写 `ApplySlot`（基类只算状态，不碰视觉） |
| `<前缀>TalentTree.prefab` | 挂好基类 `TalentTreeUIBase`、`treeAsset` 已指好、`slots` 已按节点预填的 prefab | 打开后把节点拖进 slot / 或拖 `<前缀>TalentUI` 上去替换基类 |

文件里的 `#region GENERATED` 块重生成会被覆盖，`#region USER` 块原样保留——所以"重跑生成器"
不会冲掉你手写的资源/绘制逻辑。

### 「口子」与拖节点

`TalentTreeUIBase` 上有一个 **`slots` 列表**（就是你要的"口子"），每个 `TalentNodeSlot` 持有一个
`node` 引用。因为 `TalentNode` 是**树资产的子资源**，你可以在 Project 窗口展开树资产，
把**单个节点**直接拖进 prefab 里某个 slot 的 `node` 字段（或拖进 UI 脚本上对应的槽位）。
生成器已经按节点把 slots 预填好了，你只需核对 / 重排。

### 解锁 / 点亮 / 可点 从哪来

全由框架的 `TalentRuntime` 推出，UI 只是消费状态：

- `CanUnlock(id)` → 所有前置已解锁 && 未满级 → **可点（高亮）**
- `IsUnlocked(id)` → **点亮（填充态）**
- 否则 → **锁定（灰、不可点）**
- 点击槽位 → `TryUnlock(id)`：校验 `CanUnlock` + 经 `ITalentResourceProvider` 扣点 → 置位 → 触发 `OnChanged` → UI 重绘

### 接入（游戏侧）

```csharp
using HYC.Framework.Talent;

// 1) 把生成的控制器(既是状态机又是资源提供器)建出来
var ctrl = new MyTreeTalentController();   // 构造里 Resources = this
// 2) 把 prefab 里的 UI 脚本 Initialize 一下, 它内部会 Build 树 + 绑定状态机
ui.Initialize(ctrl);
// 之后点节点 → TryUnlock → 自动扣点 + 重绘, 全链路开箱即用
```

点数体系（力量 / 金币 / 技能点……）**框架不内置**——只在 `MyTreeTalentController` 的
`#region USER` 里按 `attrKey` 去你自己的存档 / 角色属性查、扣即可。`attrKey` 来自天赋树的"黑板"，
真正数值由它指向的配置行决定，框架只认 key。

## 坑

1. **图必须无环，编辑器会拦，运行期 `Validate` 也会查。** 有环意味着"解锁 A 需要解锁 B，
   解锁 B 需要解锁 A"，玩家永远点不亮。

2. **多个入口是合法的，不要指望校验拦你。** 一棵树可以有好几条并行的起始分支（入度为 0 的节点
   可以有多个），校验不会因此报错。只有"所有节点都有前置"这种成环的情况才会被拦。

3. **节点消耗引用的是 `attrKey` 字符串，不是对象引用。** 改了黑板上的 key，
   所有引用它的节点消耗会立刻失效——校验会报错，但不会自动帮你改。

4. **`ConfigRowRef` 存的是 typeName + id，不持对象引用。** 配置资产被删除或 id 变了会变成悬空引用；
   `displayName` 是当时的快照，用于引用断了还能看清原本指向谁，别用它做逻辑判断。

5. **消耗按"每级"计，不是"解锁一次性"。** `maxLevel=1` 时两者等价，超过 1 就一定要分清——
   策划填表时最容易在这里出错。

6. **本地化 Key 只能选，不给手填。** 手填的 key 拼错了编译期和校验器都发现不了，
   要到运行期界面空白才暴露。所以这个字段**没有输入框**，只有按钮 + `LocKeyPickerWindow`；
   选完还会立刻比对本地化表，查不到就标红。新增同类字段时请沿用这个做法，别为了省事给个 `TextField`。

7. **编辑器里的 `Undo.RecordObject` 必须在"确认值变了之后、赋值之前"调用。**
   早期版本放在 Inspector 开头每帧调用，结果每次 Repaint 都往撤销栈塞一条，Ctrl+Z 直接失效。

8. **圆角纹理内部必须纯色。** 行为树编辑器当初在这里踩过：任何内部渐变经 9-slice 拉伸后
   会变成横跨节点的色带。`BTEditorStyles` 的圆角纹理只保留 alpha，不画渐变。
   天赋树**不再自带样式类**，直接复用 BT 的那一份——改一次两边同时生效，也顺带保证
   两个编辑器的观感不会因为各改各的而漂移。

9. **切换树必须重建 `TalentGraphIMGUI` 实例，不能只 `SetAsset()`。**
   这不是洁癖：视图状态（`Pan` / `Zoom` / 选中集）是实例字段，换树不换实例就会带着上一棵树的
   缩放和平移去画新树，新树布局在原点附近时**画布看起来是空的**——这正是"点左边列表，
   右边什么都不显示"的直接原因。现在的做法是 `OpenTree` 里 `new TalentGraphIMGUI(asset)`，
   并在构造/设资产时置 `_pendingFit`，等 `DrawGUI` 拿到真实 `_canvasRect` 后做一次 `ZoomToFit`。

10. **在 `OnGUI` 回调里重建 `IMGUIContainer` 是不安全的。** 新建树、从左栏切树都会导致
    宿主重建容器，如果当场执行，Unity 正在遍历的那棵 VisualElement 树就被拆了。
    所以 `OnRequestNewTree` / `OnRequestOpenTree` 统一走 `EditorApplication.delayCall` 推迟一拍。

11. **端口命中必须先于节点命中。** 输出端口圆心正好画在卡片底边（`yMax`）上，
    鼠标压在圆点上时有可能已经落在节点 rect 之外。先测节点再测端口会永远连不上线。

12. **右栏每个分组若要读 `Event`，签名必须显式带 `Event e`。**
    调用链是 `DrawGUI → DrawRightPanel(Event e) → DrawXxxSection(x, y, w)`，
    中间不会自动传下去。漏一个参数，方法体里的 `e.xxx` 就是 CS0103。
    （这个错静态扫描抓不到——正则看不见作用域。）

13. **删除当前打开的树后窗口会闪一下再恢复。** `Update()` 里有守卫，检测到 `_current` 被销毁
    会自动切到剩下第一棵。这个坑行为树编辑器当年漏过，删完树整屏空白且无人恢复。

14. **资产最好统一放 `Assets/TalentTrees/`**。新建按钮会建在这里，但手动拖别处也能用，
    只是列表扫描是全局 `FindAssets`，树多了首屏会慢。

15. **`TalentNode` 是 ScriptableObject 子资源（挂在树资产下）。** 编辑器建节点时用
    `ScriptableObject.CreateInstance` + `AssetDatabase.AddObjectToAsset` 把它挂到树资产上——
    所以能在 Project 窗口展开树资产，把**单个节点**直接拖进 UI 的 slot。节点**不能**用 `new` 构造。
    没落盘的临时树，节点是内存 SO，保存时由 `TalentTreeWindow` 统一补 `AddObjectToAsset` 落定。

16. **「生成代码」产出的 prefab 用基类 `TalentTreeUIBase` 挂好 slots**，节点已预填；
    编译通过后把生成的 `<前缀>TalentUI` 拖上去替换基类即可拿到自定义 `ApplySlot` 绘制。
    资源点数(力量/金币/技能点)不在框架里——只在生成的 `<前缀>TalentController` 的
    `#region USER` 里接 `ITalentResourceProvider`。框架只管"能不能解锁 / 解锁后改状态"的规则。

17. **`TalentNode` 必须单独一个文件 `TalentNode.cs`。** Unity 只给「与文件同名的类」生成
    `MonoScript`，而 `AddObjectToAsset` 把子资源写进 `.asset` 时必须解析到它——否则子资源会以
    "missing script" 落盘，重新导入后变成 `null`。现象就是：**树里节点全没了、连线全悬空、
    左栏计数还在**（`nodes` 列表长度还在，元素都是 null）。所以 `TalentNode` 不能和
    `TalentTreeAsset` 挤在同一个 `.cs` 里——这也是它从 `TalentTreeAsset.cs` 拆出来的原因。
    > ⚠️ **2.0.6 破坏性变更**：`TalentNode` 由普通 `[Serializable]` 类改成子资源后，**2.0.6 之前
    > 保存的树资产节点读不出来**（内联数据读不进对象引用；黑板与连线不受影响）。画布会提示
    > 「节点数据已失效」并给出「清理失效节点」按钮，清理后重新添加节点即可。
18. **`ZoomToFit()` 不能在全 null（失效）节点上跑。** 若树里节点全为 `null`，取 min/max 的循环一次都不执行，
    `minX/minY` 停在 `float.MaxValue`、`maxX/maxY` 停在 `float.MinValue`，算出来
    `Pan = (minX - pad, …) ≈ ±3.4e38`、`Zoom` 被 clamp 到 0.25。此后：
    - `ScreenToCanvas` / `_visibleCanvasRect` 因浮点精度吞掉画布尺寸而退化成零尺寸矩形；
    - 画布的视口裁剪 `NodeRect(n).Overlaps(_visibleCanvasRect)` 把所有节点判为不可见 → **画布永远空白**；
    - 新建节点时 `CanvasCenter()` 同样是垃圾值，节点被放到 ±3.4e38。
    **现象极具迷惑性：左栏计数、右栏「节点数」都对，`minimap` 里还能看到节点块（它用 `NodeRect` 直画、不做裁剪），
    就是画布上什么都没有。**
    因而：`ZoomToFit` 只统计**有效**节点、无有效节点时复位视图；新增 `SanitizeViewAndPositions()`
    每帧自愈（复位垃圾 `Pan/Zoom` + 把垃圾坐标重排回网格）；`AddNode` 落点兜底。
    > 一般规律：任何"从一组对象求包围盒再取景/裁剪"的代码，都要先处理**空集**——否则 `float.MaxValue`
    > 与 `float.MinValue` 会算出 ±3.4e38 级的荒唐数值，比崩溃更难查（画面只是"空"，不报错）。
19. **`ScriptableWizard` / `EditorWindow` 同样必须独立文件。** 这条与 #17 是同一条 Unity 规则，但后果不同：
    ScriptableWizard / EditorWindow 靠 `MonoScript` **序列化自身字段**，类名与文件名不一致时，
    - 窗口顶部 `Script` 槽显示 `None (Mono Script)`；
    - 通过 `DisplayWizard<T>()` 之后设置的字段（如 `asset`）在窗口重绘/域重载后**丢失**。
    天赋树这里的具体症状：`生成天赋树代码 / UI` 一打开就报「**没有可生成的天赋树资产**」、`asset` 为 `null`。
    `TalentGenerateWizard` 原先挤在 `TalentCodeGenerator.cs` 里 —— 已拆到独立 `Editor/Talent/TalentGenerateWizard.cs`，
    并加了一层静态兜底（`OnWizardUpdate` 里 `asset == null` 时从 `_pendingAsset` 恢复）。
    > 判据：**凡是 Unity 会为其生成 `MonoScript` 的类型**（`MonoBehaviour` / `ScriptableObject` /
    > `EditorWindow` / `ScriptableWizard`）**都必须独占一个"类名 = 文件名"的 `.cs`**。纯 C# 类（如 `TalentGraphIMGUI`
    > 那种手写画布类）不受此限。新增这类类型时，第一件事就是单独建文件。
