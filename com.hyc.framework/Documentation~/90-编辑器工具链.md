# 90 · 编辑器工具链

> 编辑器代码量约为运行时的 1.8 倍——这个框架的价值大半在工具链。

## 菜单分档与 priority（改菜单前必读）

菜单**不是字母序，而是按使用频率与语义分三档**：

```
HYC Framework/
├── ① 内容制作（高频）Config / BT / UI / Localization / Attributes / Talent
│─────────────────── 分隔线 ───────────────────
├── ② 通用工具      Tools / Assets
│─────────────────── 分隔线 ───────────────────
└── ③ 项目级（低频）Settings / Samples
```

**分隔线不是画出来的**，是 priority 差 ≥ 11 自动生成的：
`Cinemachine(81) → Tools(100)` 差 19、`Tools(103) → Settings(200)` 差 97 ⇒ 恰好两处。
档内相邻差均 ≤ 10 ⇒ 档内不画线。

⚠️ **Unity 菜单的硬限制**：菜单**不支持自定义分组标题**，只能画分隔线。
所以"分级"只能靠**位置语义**表达——这正是**排序比命名更重要**的原因。

⚠️ **不能只给父菜单首项写 priority**：排序作用于每个叶子菜单项，
未写 priority 的默认 **1000**（不是 0），会直接沉到整个菜单最底部、越过 `Settings(200)` 与 `Samples(210)`。
故当前 **44 个可见菜单项逐个**都标了 priority（见上表右侧）。

<details>
<summary>priority 的官方规则（两次踩坑记录）</summary>

Unity `MenuItem(itemName, isValidateFunction, priority)` 的 `priority` **不只是排序**，
它还隐式控制**分隔线**：

> **相邻两项的 priority 差值 ≥ 11 时，Unity 会在它们之间画一条分隔线。**
> （官方文档示例用 100 与 111；改成 110 差 10 就**没有**线）

- **第一次错**：`BT/导出 Blob(打包用)` 写了 `priority = 30`，与前一项（0）差 30
  ⇒ BT 子菜单上方凭空多出一条线，视觉上像"HYC Framework 标题"与"BT"分属两组。
- **第二次对**：为做分档给每项显式标 priority。**父菜单排序由它首个子菜单的 priority 决定**，
  所以父菜单顺序也靠首项控制；新增/删除菜单时必须重新核算整套数值。

完整约定见 [`com.hyc.framework/Editor/MenuLayout.md`](../com.hyc.framework/Editor/MenuLayout.md)。

</details>

## ⚠️ MenuItem priority 会画出莫名分隔线（踩坑记录）

Unity 的 `MenuItem` 第三个参数 `priority` **不只是排序**，还隐式控制分隔线：

> **相邻两项 priority 差值 ≥ 11 时，Unity 会在它们之间画一条分隔线。**
> （官方文档示例用 100 与 111；改成 110 差 10 就**没有**线）

本框架踩过一次：`HYC Framework/BT/导出 Blob(打包用)`<!-- 历史名称，勿删；2.0.6 起改名 -->
曾写 `priority = 30`，
与前一项（priority 0）差值 30 ⇒ **BT 子菜单上方凭空多出一条线**，
视觉上像是"HYC Framework 标题"与"BT"分属两个分组。

**现行约定（2026-10-07 菜单三档重组后，与 `Editor/MenuLayout.md` 一致）**：
**每个 `[MenuItem]` 都显式写 priority**，值落在三档区间内——内容制作 0–81 / 通用工具 100–102 / 项目级 200–210。
没写 priority 的项默认为 0，会全部挤到最前面打乱分组（这是重组时踩过的第二个坑）。
另注意**父菜单排序由其第一个子菜单的 priority 决定**，所以调大类顺序得改子项 priority。
档间差 ≥ 11 自动生成分隔线（如 `Cinemachine(81) → Tools(100)`），档内差 ≤ 10 不画线。
完整结构图与数值见 `Editor/MenuLayout.md`。

#### 通用导出层：模态清单窗（`Editor/Export/` → `HyExportEngine` / `HyExportWindow`）

**所有 HYC 导出共用的唯一导出窗**。调用方不再自建窗口，只提供「作业行 + 可选回调」：

```csharp
HyExportEngine.Run(new HyExportRequest {
    title = "导出 …",
    description = "……",          // 显示在列表顶部；危险操作的说明也放这里
    destructive = true,           // 需连点两次「执行」（按钮文案变「确认执行?」）
    prepare  = () => true,        // 弹窗后、逐行执行前的一次性准备（落盘 / 清目录）
    finalize = () => { AssetDatabase.Refresh(); return true; },  // 整个操作唯一一次刷新
    jobs = { new HyExportJob { name = "XxxConfig", count = 12, unit = "个资产",
                               run = () => ConfigExportService.ExportAll(t, true, true, false) } },
    onFinished = summary => { /* 错误窗 / 刷左树 / 日志 */ },
});
```

- **三态窗口**：**预览**（只画列表 + `取消` / `执行`，**零副作用**）→ **执行**（只有 `中止`，没有关闭按钮）→ **完成**（结果条 + `关闭`）。导出中没有关闭按钮是刻意的：避免用户中途去点别的菜单再触发一次导出、重复写产物。
- **不再有确认对话框**：危险操作的说明文字直接进列表顶部，确认动作就是窗内的执行按钮。`ConfigDataTree.CleanAndExportAll` 里原先那个 `EditorUtility.DisplayDialog("全量清理后全量导出", …)` 已删除。
- **模态 + 推进靠窗口 `OnGUI`**：`ShowModalUtility` 走原生 `MakeModal` 模态消息循环，**阻塞调用方且不跑 `EditorApplication.update`**，只泵 GUI 事件——所以 `Step()` 由窗口每帧 OnGUI 调用（只在 `EventType.Layout` 阶段推进一次，保证同帧 Layout/Repaint 的可见行集合一致）。
- **推进节奏**：`Preparing` / `Working` / `Finalizing` 三段各自两拍——上一拍只更新阶段文案并画一帧，下一拍才真正干活；`Working` 每帧只走**一行**，且先标「进行中」让窗口画出来再执行，所以每行都能看到「进行中 → 打勾」。单行作业本身是原子的，超大表仍可能占满一帧。
- **列表虚拟化**：行数可能上千（实测工程 1017 行），ScrollView 里**只画可视区约一屏行**，上下用 `GUILayout.Space` 占位保持滚动范围；可见行映射与区间只在 `EventType.Layout` 阶段算好缓存，`Repaint` 只读，保证同帧两次事件的控件集合一致。不虚拟化时单帧 IMGUI 控件上万，主线程被钉死会弹 Unity 的 "Hold on (busy for 10s)"。
- **准备阶段同样是单帧同步活**：`prepare` 在 `OnGUI` 的 Layout 里跑，绝不能做「遍历全目录资产逐个 `SetDirty` 再 `SaveAssets()`」这类全量重写——那会把主线程占满十几秒并弹 busy 框。`ConfigExportService.SaveFolder` 只调一次 `AssetDatabase.SaveAssets()`（Inspector / `SerializedObject` 编辑已自动标脏）。
- **末尾单次 `Refresh`**：循环内不再逐行 `AssetDatabase.Refresh()`（原实现 N 类型 = N 次全量刷新，是卡死主因）。`ConfigBaseExport.ExportCore` / `ExportAllCore` 与 `ConfigEnumCodeGen.WriteFile` / `Export` 都有 `refresh` 开关；批模式（CI）走同步入口，同样只在末尾刷一次。中止 / 取消时 `finalize` 不跑，由 `onFinished` 补一次刷新（已完成行的产物还是要落盘）。
- **逐行进度**：一行 = 一个作业（名称 / 计数 / 状态），完成后打勾停留片刻再淡出移除；行内计数复用预检那次 `CollectConfigAssets`，不再逐类型跑全工程 `FindAssets`。
- **错误汇聚**：`HyExportEngine.Report` 收集，运行期只收不发（模态循环内 `DisplayDialog` 会变成嵌套模态），结束后一次性开 `BuildErrorWindow`。
- **`SafeClose()` 刻意偏离「关窗走 `delayCall`」约定**：`delayCall` 走 `EditorApplication.update`，而模态循环不泵 update——照约定写会把窗口永久留住。改为同步 `Close()` + `mClosing` 幂等 + 关完 `GUIUtility.ExitGUI()` 中止本帧剩余布局，`OnGUI` 里对 `ExitGUIException` 重新抛出（正常退出信号，不是绘制异常）。偏离原因写在方法 XML 注释里。
- 原型见 `export_center_ui.html`（不提交；旧的 `config_export_list_ui.html` 已被它取代）。
- **尚未迁移**：BT / SceneContent / Map / Audio 的导出仍走各自老路径（同步、无逐行进度），后续按同一模式接入本层。

要点：

- **文件夹右键的导出项按内容动态列出**：集中在「导出」**真子菜单**里（GenericMenu 路径按 `/` 拆子菜单）——每种可导出配置类型一项「短名（N 个）」+ 子菜单内分隔线 + 「导出全部」；枚举 / 模板作为顶级动态项单列（模板是生成代码不是导出）。N 与 `ExportFolder` 同一过滤规则实时统计，三类皆无时列禁用提示。模板文件夹不再出现不适用的「保存并导出内部所有」。详见 [12 篇](./12-数据编辑与校验.md)。
- **按类型导出必须整类型导**：`ConfigBaseExport.ExportCore`（单资产）对 Blob 格式只写这一个资产，逐资产循环调会互相覆盖；按类型/文件夹导出走 `ExportAllCore`（一类型一个产物文件）。
- **「全量清理后全量导出」会删文件**：配置侧清空 `ClientExportDir` / `ServerExportDir` 下的 `*.blob`，
  BT 侧清空整个 `StreamingAssets/BTBlob/`。用于「删了表 / 改了名之后残留幽灵产物」的场合，
  **日常增量不要用**。
- **局部导出不删旧产物**：`ExportTrees` / `ExportFolder` 只覆盖这批 blob，
  再 `SyncManifest` 重扫目录重建清单，保证 manifest 与实际文件一致，真机读得到。
- **导出前必须先存盘**：配置侧的 `SaveFolder`（一次 `AssetDatabase.SaveAssets()`）与 BT 侧的存盘步骤都不能省，
  否则导出的是内存里尚未落盘的数据。

#### 配置资产索引：`ConfigAssetIndex`（全包唯一数据源）

**「配置数据库」**：左侧树、右键菜单、导出预检 / 拆行 / 收集、类型文件夹归置等所有「要拿配置数据」的地方，
都只读这一份索引，不再各自 `AssetDatabase.FindAssets` / `LoadAssetAtPath` 全扫。

- **存的字段**（`ConfigAssetIndex.Entry`）：`Path`（规范化路径，主键）、`Guid`、`AssetType`（精确类型）、
  `Folder`、`FolderGuid`（父目录位置）、`TypeFolder`（应归置的类型文件夹名）、`Asset`（**懒加载**，首次访问才反序列化）。
  类型 / 数量 / 位置等派生视图由主表增量维护，后续要加字段直接扩 Entry。
- **视图**：`All()`、`ByType(Type)`（精确类型桶，O(1)）、`CountByType(Type)`、`ByFolder(folder)`（含任意深度子目录）、
  `ByTypeAssignable(Type)`（含派生类型，对齐 `FindAssets("t:Type")` 语义）。派生视图按 `Revision` 缓存，
  结构不变时 O(1)。索引只登记事实，**不做业务过滤**——是否可导出 / 是否枚举 / 模板
  仍由各调用方按原有条件判断，因此接入前后行为一致。
- **更新（增量，避免重建）**：
  - `OnPostprocessAllAssets` → `Upsert` / `Remove` / `Move`，只动受影响的桶；
  - 域重载后静态字典清空且 Unity 不重导入未变动资产 → `[InitializeOnLoad]` + `delayCall` 补一次 `Rebuild()`
    （**整个会话唯一一次全量扫描**）；
  - `projectChanged` 防抖 150ms 兜底：仅在导入钩子**未**处理过本次变更时（外部 VCS 拉取等）才 `Reconcile()`
    做 GUID 差集对齐，日常 Ctrl+S 零额外扫描；
  - 菜单「刷新」显式调 `Reconcile()`，不重建结构。
  - 每次结构变更 `Revision++`，调用方据此判断派生缓存是否过期。
- **回调安全铁律**：`TryPeek(path)` 是唯一纯内存查询，可在禁止调用 AssetDatabase 的
  `AssetModificationProcessor.OnWillMoveAsset` 里使用；`All/ByType/ByFolder` 会 `EnsureReady()`，
  只能用于普通编辑器上下文。`ConfigAssetLayout.Register/Unregister/WarmupTypeFolderCache` 保留公开签名，
  内部转调索引（旧的类型文件夹缓存已并入）。
- **导出注入**：`ConfigExportRunner.GroupByExactType` 一次遍历按 `GetType()==键` 精确分组，
  窗口计数与真正导出的资产列表同源（修掉了旧 `CountByType` 用 `IsAssignableFrom` 导致派生类资产计数虚高）；
  经 `ConfigExportService.ExportAll(..., suppliedAssets)` → `ConfigBaseExport.ExportAllCore(..., suppliedAssets)`
  注入。**两者都是新增可选参数**，既有调用与生成的 `XxxExport` 代码无需改动。
- **建树 / 右键**：`ConfigDataTree.InstallFiles`、`LoadAssetsUnder<T>`、`HasAnyAssetOfType`、`GetFolderStats`
  全部改为读索引；旧的 `mFolderStatsCache` / `ComputeFolderStats` 已删除（索引按 Revision 自动失效）。
- **其余配置读取点**：`ConfigDataWindow` 的模板枚举保存、`ConfigEnumCodeGen.LoadAllEnums`、
  `ConfigIconApplier` 的 `SyncAll` / `FindTemplateForType` / 菜单兜底（走 `ByTypeAssignable`），
  均改读索引。
- **刻意不接**（语义不同，硬套会改变行为）：`FolderConfigEditor` / `ConfigDataTree` 里
  `FindAssets("", folder).Length`（数的是文件夹全部资产，不止 `.asset`）、框架级模板目录
  `FrameworkTemplatesFolder`（包内资产，不属于配置根）、`ConfigExcelImporter` 的按名搜索与
  `ConfigExcelPendingImport` 中间态、`DuplicateIdGuard` 的 `TalentTreeAsset`、`GUIDrawer` 的 `BTTreeAsset`。

## 注意事项 / 坑

1. **`Clean Missing Asset References` 会直接改资产文件**——跑之前确保工作区干净，方便回滚。
2. **NPOI 只在编辑器可用**——别在运行时代码里引用 `LocalizedExcelReader` 或 NPOI 类型。
3. **`DataEditor/` 大量字段抽屉依赖 `ConfigFieldType`**——加新字段类型时，抽屉渲染要同步加分支，否则新类型在编辑器里显示不出来。
4. **BT 编辑器是纯 IMGUI**，没有 UXML/USS；改界面直接改 `BTGraphIMGUI.cs` 的绘制代码。
5. **画布不做 GUIClip 裁剪**——新增任何面板/浮层都要画在画布之后，否则会被节点盖住或反过来盖住节点。
