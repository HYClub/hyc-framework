# 10 · 配置管线（Config）总览

## 职责

把 Excel / 模板定义的配置表，在**生成期**烘焙成不可变 Blob，**运行期**以世界无关的静态表提供无分配查询。

一句话：**编辑期是 ScriptableObject + 生成的代码，运行期只有一个 Blob 指针。**

---

## 全链路

```
① 配置模板 ConfigTemplate        定义表结构与字段
        ↓  （Editor：代码生成）
② 生成的 C# 类 [CfgAsset]        blittable struct，命名空间 {root}.config（root 见 HYC Settings → CodeGen）
        ↓  （Editor：数据编辑器填数据）
③ 配置资产 .asset                每行一个数据条目
        ↓  （Editor：导出）
④ BlobAssetReference<BlobRoot<TRow>>
        ↓  （Bootstrap：注册）
⑤ ConfigRegistry 静态表（框架内部，宿主不可见）
        ↓  （运行期：查询）
⑥ 玩法系统 / UI 走门面 {ns}.ConfigManager.{Type}.GetByID(id)
```

---

## 核心类

| 类 | 位置 | 职责 |
| --- | --- | --- |
| `ConfigTemplate` | Runtime | 表结构模板（本身也是一个配置资产 `模板/配置模板`，可在数据编辑器里重新打开再生成） |
| `ConfigTemplateField` | Runtime | 单个字段定义：类型、列表、导出目标、检查规则、客户端/服务端导出设置 |
| `ConfigRegistry` | Runtime | 运行期低层注册表——**框架内部机制**（生成的 `XxxBlobSystem` 注册、门面背后）；宿主禁用，见「运行期查询 API」铁律 |
| `{ns}.ConfigManager`（生成） | `{OutputDir}/ConfigManager.cs` | **宿主唯一查询入口**：每类型一个嵌套类，`GetByID(id)` → `ref Cfg{Type}`（可写 ref）；遍历全表走 `Count` + `GetByIndex(i)` |
| `ConfigBlobTable<TRow>` | Runtime | 单张表（内部持有 `BlobArray<TRow>`） |
| `BlobTable` | Runtime | Blob 构建/读取辅助 |
| `IConfigIdProvider` | Runtime | ID 分配策略（`LocalConfigIdProvider` / `NetworkConfigIdProvider`） |
| `ConfigGenerator` | Editor | 由模板生成 C# 类 |
| `ConfigExportService` | Editor | 把数据烘焙成 Blob 并导出（客户端/服务端可分开） |
| `ConfigValidator` | Editor | 校验（`HYC Framework/Config/Validate Config`） |

## 运行期查询 API

### 宿主唯一入口：生成式门面 `{ns}.ConfigManager`

代码生成时为每个配置类型产出一个嵌套查询类（落 `{OutputDir}/ConfigManager.cs`），静态、无 World 依赖、零字符串键。三种典型用法：

```csharp
// ① 按 id 查一行（零拷贝 ref，未命中抛 KeyNotFoundException）
ref var row = ref ConfigManager.FashionRow.GetByID(1001);
int price = row.Price;

// ② 遍历全表：Count 作循环边界，GetByIndex(i) 按行序取（同样零拷贝）
for (int i = 0; i < ConfigManager.FashionRow.Count; i++)
{
    ref var r = ref ConfigManager.FashionRow.GetByIndex(i);
    Debug.Log(r.Price);
}

// ③ 缺失兜底：try/catch + ref 返回助手（静态默认行也以 ref 返回，全程零值拷贝，见下）
ref var proj = ref ResolveProjectile(projId, out var fromConfig);
```

- **类型安全、零字符串键**：`ConfigManager.FashionRow` 就是类型本身，没有字典查找、没有字符串键拼错的空间。
- **零拷贝**：`GetByID` / `GetByIndex` 返回**可写 `ref`**（刻意不用 `ref readonly`——C# 禁止把 ref-readonly 返回值绑到 `ref var` 局部变量，CS8329；而 Entities 分析器又要求 blob 行的局部变量必须是非只读 ref，EA0001，`ref readonly var` 同样被拦。两端夹逼下可写 ref 是唯一合法形态，只读靠纪律保证），直接指向 Blob 内该行，不复制结构体；返回的 ref 在表注册期间有效，不要跨帧缓存。
- **`GetByID` 未命中抛 `KeyNotFoundException`**——这是刻意语义：查询入口（`Reference` 字段 / 数据表 id）理论上必然存在，"没这条"是数据错误，应当响亮失败。确需宽松语义（未命中不抛）时用门面 `ConfigManager.{Type}.Contains(id)` 预判存在性，命中再 `ref var row = ref GetByID(id)` 取行——**不得**走 World 扩展 `world.GetCfg{className}(id)`：它返回 blob 行的值拷贝、未命中返 `default`，二者都是 EA0001 运行期炸弹，已从生成器删除（详见下方铁律段）。
- **③ 缺失兜底**（行理论上必然存在，但表现层不能因数据错误崩）：把读取逻辑整体放进 `try`，ref 局部变量只在 `try` 内存活——`try { ref var row = ref ...GetByID(id); ...读取... } catch (System.Collections.Generic.KeyNotFoundException) { ...回退... }`。兜底值若也是行结构（如默认武器行），用「ref 返回助手 + 静态默认行」：`private static ref CfgX ResolveX(long id, out bool hit)` 内部 `return ref ...GetByID(id)` /  catch 里 `return ref s_default;`，调用方统一 `ref var x = ref ResolveX(id, out var hit);`。
- 门面只收录**已生成 Blob 结构**的类型（模板没配客户端导出字段时不会出现）；随「生成代码」自动同步。

### ⛔ blob 行必须 ref 访问（EA0001，写错=运行期内存错误）

`GetByID` / `GetByIndex` 返回的可写 `ref Cfg{Type}` **必须整个放进 ref 局部变量**：

```csharp
ref var row = ref ConfigManager.FashionRow.GetByID(1001);   // ✅ 正确
var  row =  ConfigManager.FashionRow.GetByID(1001);          // ❌ EA0001 编译错
CfgFashionRow row; row = ConfigManager.FashionRow.GetByID(1001);  // ❌ 值拷贝，寻址错位
```

**为什么这么严**（Unity.Entities 1.0.16 源码实证）：`Cfg{Type}` 行结构含 `BlobString` / `BlobArray` 字段，它们的偏移是**自相对**的——`BlobArray<T>` 索引器与 `BlobString` 取址都是 `(byte*)&m_OffsetPtr + m_OffsetPtr`（相对**字段自身地址**，不是 blob 基址）。把行**值拷贝**到栈上后，拷贝里的偏移量相对栈地址解析即**寻址错位**：开发构包（`ENABLE_UNITY_COLLECTIONS_CHECKS`）直接抛 `InvalidOperationException`（`ThrowOnCopyOfBlobArrayFields`），正式包**静默读出垃圾数据**。所以 ref 不是风格问题，是正确性硬需求。

**ref 局部变量的硬约束**（违反=编译错或潜在崩溃）：

- **不能跨方法传递**：`void M(CfgX x)`、`M(in row)`、`out row` 全会被分析器拦（EA0009）——要传就传 id，方法内部自己查（查表是 O(1) 索引，代价可忽略）。
- **不能存进字段 / 数组 / List**，不能被 lambda 捕获，**不能跨帧缓存**——ref 只在表注册期间有效，切场景 / 重注册后即成悬垂 ref。
- **行内 blob 字段也要 ref**：`ref var arr = ref row.SomeBlobArray;`（只有 `.Length` + 下标，没有遍历器）；`BlobString` 字段直接 `row.SomeText.ToString()`。取行内数组字段的 ref 时，行变量本身必须是非只读的 `ref var`（只读 ref 拿不到可写子 ref）；且门面返回的本来就是可写 ref——`ref readonly var` 既绑不上（CS8329，见上）也被分析器拦（EA0001）。所以本规范统一教 `ref var` 而非 `ref readonly`。
- **只读是纪律**：blob 资产是不可变数据，别通过 `ref var` 往行里写——写坏没有兜底。

### ⛔ 铁律：宿主禁止调用 `ConfigRegistry`

`HYC.Framework.Config.ConfigRegistry`（`Register` / `Has` / `AllTypes` / `TryGet` / `Get` / `GetRef` / `GetRowRefAt` / `Contains` / `GetAllRows` / `TryGetRowAt` / `GetRowCount` / `Materialize` / `Clear`）是**框架低层注册表**，属生成代码与加载系统的内部机制，**宿主代码不得调用**：

1. **不受兼容承诺**：门面是框架对宿主承诺的稳定查询入口；低层类型的 API 形态可能随版本演进调整，宿主直接调用等于把升级风险接进业务代码。
2. **宿主代码里只应有一个 `ConfigManager` 解析目标**：门面与低层曾同名，直接造成 CS0104（二义）/ CS1061（解析错对象）两类编译错——禁用低层从根上消除。
3. **职责分离**：注册（造表）是加载系统的事，查询（用表）才是业务代码的事；混在一起等于把数据加载细节漏进表现层。

**唯一例外**：宿主**自建 Blob 加载系统**（不采用生成的 `XxxBlobSystem` 时才发生）可调 `ConfigRegistry.Register(table)`——那是"造表"不是"查表"。普通业务代码永远只查不注册。

以下低层 API 仅列作**参考**（框架生成代码 / 自建加载系统使用场景），宿主业务代码请回到门面：

```csharp
// ↓ 低层参考——宿主业务代码禁用
ConfigRegistry.Register(myTable);                      // 造表：注册一张 ConfigBlobTable<TRow>
bool has   = ConfigRegistry.Has<FashionRow>();         // 某类型表是否已注册
var all    = ConfigRegistry.GetAllRows<FashionRow>();  // BlobArray<TRow>，表未注册返回 default
int count  = ConfigRegistry.GetRowCount<FashionRow>(); // 已加载行数
ConfigRegistry.Clear();                                // 切场景/重进游戏时回收（对 IDisposable 的表 Dispose）
```

### 要点

- 门面 `GetByID` / `GetByIndex` 的行类型 `TRow` 约束 `unmanaged`——行必须是 blittable 结构体。
- **门面取行必须 `ref var row = ref ...`（EA0001）**——值拷贝 blob 行 = 寻址错位（dev 抛 / release 读垃圾），详见上一节；ref 不能跨方法传递 / 存字段 / 闭包捕获 / 跨帧缓存。
- 门面 `GetByID` 未命中抛 `KeyNotFoundException`：要么接受响亮失败、要么用门面 `Contains(id)` 预判存在性、命中再取行，**不要**为绕开语义去调低层 `TryGet`。World 扩展 `world.GetCfg{className}(id)`（值拷贝 + 未命中返 `default`，EA0001 炸弹）已从生成器删除，统一走门面即可。
- **不需要 World 句柄**，UI 层可以直接查。

## 模板（ConfigTemplate）字段

| 字段 | 说明 |
| --- | --- |
| `displayName` | 显示名，支持 `分类/名称`，如 `装备/时装` |
| `className` | 生成的 C# 类名，如 `FashionConfig` |
| `lastGeneratedClassName` | 上次生成时的类名，用于检测改名并触发改名处理（`HideInInspector`） |
| `baseTemplate` | 基类模板，生成的类继承它；基类字段以只读展示 |
| `iconBuiltInName` | 内置图标名（`EditorGUIUtility.IconContent`） |
| `iconCustom` | 自定义图标（项目内 `Texture2D`），优先级更高 |
| `fields` | 字段列表 |

**图标传播**（`Editor/DataEditor/ConfigIconApplier.cs`）：模板图标会同步到 Unity 原生 Project 窗口的**生成类型 MonoScript（类级）**——该模板生成的全部配置资产经类图标继承显示。注意 `EditorGUIUtility.SetIconForObject` 只接受 GameObject / MonoScript，传 ScriptableObject 实例时图标会记到该实例的类上、同类全部资产共享，因此**单个模板资产自身的原生窗口图标通道不存在**；模板自身的图标仅由框架自绘界面消费（数据树行 / 检查器缩略图读模板字段，逐模板生效）。持久化分两层：自定义纹理经 `MonoImporter.SetIcon` + `SaveAndReimport` 写进生成类 `.cs.meta`（跨会话 / 换机 / 进 VCS 有效）；内置图标（内置纹理无 GUID 写不进 meta）为 session 级，打开工程时自动验证式同步（不一致才设，已生效零操作）。即时生效点：保存模板 / 选完图标、工厂创建 / 复制资产、生成代码；手动兜底菜单 `HYC Framework/Config/Apply Template Icons`。**框架/基类模板（`generateCode=false`，如 `ConfigBase`）不参与传播**——无生成类型与配置资产，传播无意义；基类模板的 icon 字段仍可在模板编辑器内查看 / 修改（只影响数据树与检查器的自家显示）。

字段细节（类型、导出设置、检查规则）见 [11-字段类型与导出设置](./11-字段类型与导出设置.md)。

## 配置实例基数（Cardinality）

一个配置类型在工程中能同时存在几个资产实例，称为它的**实例基数（Cardinality）**。框架只支持两种：

| 基数 | 含义 | 声明方式 |
| --- | --- | --- |
| `Multiple`（默认） | 该类型可存在任意多个资产实例 | 不标 `Unique`（即 `CfgAsset(name, order)`） |
| `Single` | 全工程唯一，整个工程只应有一个该类型的资产 | `[CfgAsset(name, order, unique: true)]` |

> 概念层用 `Multiple` / `Single` 这对词汇描述意图；**代码层就是 `CfgAssetAttribute.Unique` 这一个布尔**——`Single` 投影成 `Unique=true`，`Multiple` 投影成 `Unique=false`（默认值）。目前没有第三种基数；若未来需要（如「每场景一个」），再把它升级为枚举，不要现在提前抽象。

### Single 的强制点

`Single` 不是只靠约定，而是在多个入口被强制，确保「全工程唯一」不被绕过：

| 入口 | 强制行为 | 位置 |
| --- | --- | --- |
| 类型声明 | `CfgAssetAttribute.Unique` 字段（`Inherited = true`） | `Runtime/CfgAssetAttribute.cs` |
| 创建 | 唯一类型已存在即抛 `InvalidOperationException`（"禁止重复创建"） | `ConfigAssetFactory.Create` |
| 批量创建 | 唯一类型直接抛「不支持批量创建」 | `ConfigAssetFactory.CreateMany` |
| 创建器 UI | 显示唯一标记，已存在类型不提供二次创建 | `ConfigCreateWindow` / `ConfigDataTree` |
| 导出去重 | `ConfigIdService.EnsureUniqueBeforeExport` 拦 `id == 0` / 重复项 | `ConfigExportService` 链路 |

### 要点

- **`Single` 的拦截发生在创建期**：`ConfigAssetFactory` 用 `IsUniqueType` + `HasExistingUnique`（`AssetDatabase.FindAssets` 按类型扫目标文件夹）判断。存量资产或外部拷贝若绕过创建器直接放进工程，创建期拦截拦不到——导出期的 `EnsureUniqueBeforeExport` 是第二道闸门。
- **`Hide` 与 `Unique` 正交**：`Hide` 只决定类型是否出现在「配置创建器」列表（框架基础设施类型如模板 / 基类 / 音频总览），与「是否唯一」无关；两者可在同一 `[CfgAsset]` 上同时设置。
- **声明示例**：

```csharp
// 全工程唯一的音频总览
[CfgAsset("音频/音频总览", 60, unique: true)]
public class AudioCatalogOverview : ConfigBase { /* ... */ }

// 可多个的角色配置（默认，不写 unique）
[CfgAsset("角色/角色配置", 10)]
public class CharacterConfig : ConfigBase { /* ... */ }
```

交叉引用：创建 / 导出去重的实现细节见 [12-数据编辑与校验](./12-数据编辑与校验.md)（「配置创建」与「导出前查重」）；`[CfgAsset]` 特性字段速查见 [99-Blob-与数据约定](./99-Blob-与数据约定.md) 第七节。

## 注意事项 / 坑

1. **`TRow` 必须 blittable**——字符串字段要选 `BlobString` 或 `FixedString` 导出模式（见 11 篇），否则烘焙会失败。
2. **`Materialize` 缓存会被 `Register` 清空**——引导期注册完所有表之后再开始查询。
3. **`GetAllRows` 返回 `BlobArray<T>` 引用**，不要长期持有跨 Blob 生命周期；表未注册时返回 `default`（`Length` 为 0，遍历前先 `Has<T>()`）。
4. **改了模板的 `className` 再生成**会走改名处理流程，原有数据资产要确认是否跟着迁移。
5. **每侧的导出设置决定字段进哪一侧产物**：该侧 `mode` 选 `None`（「不导出」）即该侧不含此字段，改完需要重新导出。（旧的 `exportTarget` Client/Server/Both 已移除，现保留给枚举定义用。）
