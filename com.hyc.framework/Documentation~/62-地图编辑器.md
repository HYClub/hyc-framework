# 62 · 瓦片地图编辑器（Map）

> 面向使用方：**这就是你要读的那一篇**。
> 讲清楚「怎么建、怎么画、自动边缘怎么配、怎么导、怎么在游戏里加载」，以及这套东西刻意**不做**什么。
> 原理与踩坑写在正文的「为什么」小段里，不另开设计稿。

---

## 一、它解决什么问题

Tilemap 手摆有两个绕不开的痛：

1. **边缘要对不上**。「干沙旁边是水，挨着水的那格应该是湿沙」——手工一格一格换瓦片，
   地图一大就再也维护不动；换一套美术更是全部重来。
2. **数据在场景里**。地图存在 Tilemap 组件上，既不能导出、也不好复用，
   想做「关卡从包里读」就得另起一套。

这套东西的做法：**地图只存「每格是什么值」，铺哪张瓦片由规则在加载时算**。
一张 512×512 的地图在磁盘上是 **256KB 出头**，而且**换美术、改规则都不用重导地图**。

「值」不止一种：地形是一层，通行、区域、密度各自再开一层（见 §3.5）。
每层都是 `width × height` 个字节，所以上面那个体积是**每层**的量级。

## 二、五个对象，一条链路

```
MapTileSet（瓦片集）
   ├─ materials + extraGrids   值层：第 0 层地形（沙/水/草），其后是通行/区域/密度…
   ├─ tiles                    瓦片池：扁平的一堆 Sprite，只被规则按下标引用
   └─ ruleSets                 规则集：一层 Tilemap 一套规则，各自声明读哪一层值
        │  被引用
        ▼
MapAsset（地图资产：N 层 width × height 字节网格 + 道具落点）    ← 编辑器里改的是它
        │  导出
        ▼
MapBlob（StreamingAssets/Map/<mapId>.blob）                  ← 只存各层值 + 指纹
        │  加载
        ▼
MapView（MonoBehaviour：读 Blob → 按规则集建层 → 逐格求值铺瓦片）
```

| 对象 | 类型 | 建在哪 | 谁改它 |
| --- | --- | --- | --- |
| 瓦片集 | `MapTileSet` (SO) | `Assets/Create/HYC Framework/Map/Tile Set` | 美术/策划一次性配好，所有地图共用 |
| 地图 | `MapAsset` (SO) | `Assets/Create/HYC Framework/Map/Map` | 编辑器窗口里画 |
| Blob | 二进制 | 菜单 `Export Blob` | 代码生成，**不要手改** |
| 装载器 | `MapView` (MonoBehaviour) | 菜单 `Export Prefab` 产出 prefab | 拖进场景即可 |

**三块内容不要混**：值层是玩法语义（存档、寻路、伤害都只认它），瓦片是表现，规则是两者之间的连接。
一旦让值自己持有一组固定槽位的瓦片，就退回到「一种材质只能有一种长相」，
想要「沙地贴水边变成湿沙」就只能再开一种材质，地图数据跟着膨胀。

## 三、自动边缘：A + B = C 到底怎么配

### 3.1 一句话

一格最终长什么样，由它的 **3×3 邻域**决定：

```
  TL  T  TR        下标 0 1 2      上排
   L  ●   R   →    下标 3 4 5      中排（4 = 自己）
  BL  B  BR        下标 6 7 8      下排
```

每个位置写一个**格子值**：`-1` = 通配（不参与匹配），`0` = 必须是空，`n` = 必须是材质 `n-1`。
一条规则 = 一个 3×3 图案 → 一到多张候选瓦片。所有命中同一格的结果取第一条（`breakOnMatch`）。

**这就是 A+B=C**：中心写 A、上边写 B，命中的那张瓦片就是「上半是 B、下半是 A」的**整格**过渡图。

### 3.2 用过渡向导，别手写 16 条

右侧面板 →「过渡向导」：

1. 选 **材质 A**（本层的主体，比如沙地）、**材质 B**（邻接的那个，比如水）；
2. 往 4×4 的 16 个格子里拖 16 张过渡 Sprite；
3. 点「生成 16 条过渡规则」。

位序固定：**N=1 / E=2 / S=4 / W=8**，每一位表示「那个方向的邻格是不是 B」。
16 条规则的中心都是 A，四条边按位填 A 或 B，**规则互斥**，所以顺序无关。
生成的组会插在组列表**最前面**——过渡必须优先于「底色」规则，否则底色规则会先命中把过渡盖掉。

> 这 16 张就是业界说的 16 张 Wang / 过渡集（Tiled 的 Wang 集、LDtk 的 Rules Wizard 生成的是同一套）。
> **每张都是和 A、B 同尺寸的一整格**，不是半格窄条。

### 3.3 为什么不用 47 / 256 张

| 模型 | 张数 | 能区分「邻居是谁」吗 | 能修内凹角吗 |
| --- | --- | --- | --- |
| 16 张（4 位边集） | 16 | 只区分 A / B | 否 |
| 47 张（8 邻二值规范化） | 47 | 只区分「同类 / 不同类」 | 是 |
| 256 张（8 位 × 材质） | 256×材质数 | 是 | 是 |
| **规则（本框架）** | 你写多少算多少 | **是，任意多种** | 是，补一条带对角约束的规则即可 |

47 张**做不出**「三种材质挤在一格角上」：它每一位只记「这个邻居跟我一样 / 不一样」，
没有「邻居是谁」这一维。而规则天然能写「中心=沙、右上=水、右下=草」。
需要内凹角修正时，在 16 条之后**补几条对角约束的规则**就行，不用再去找一整套 47 张图。

### 3.4 多层：河流为什么能压在草地上

一格数据只能属于一种值，但视觉常常要叠。做法是**两个规则集读同一份网格**（同一个 `sourceGrid`）：

- 规则集①「地面」：对「河」这一格铺草地瓦片（`中心=河 → 草瓦片`）；
- 规则集②「水面」：对「河」这一格铺水面瓦片（`中心=河 → 水瓦片`）。

数据一份、值一种，视觉是叠的。`ruleSets` 的**列表顺序就是图层顺序**（index 0 在最下）。

### 3.5 多网格：一个字节只能表达一件事

「这格能不能走」和「这格是什么地形」是两件事，但一个 `byte` 只能存一件。
把河做成「不可走的地形」当然可行，可一旦想要「浅水可走、深水不可走」「冰面滑但能走」，
地形种类就会膨胀成一堆只为通行服务的材质。

所以地图有**多层值**，每层一套自己的值表：

| 层 | 名字 | 值 | 谁读它 |
| --- | --- | --- | --- |
| 0 | 地形 | 沙 / 水 / 草 … | 铺地面的规则集；默认也决定能不能踩 |
| 1 | 通行 | 可走 / 阻挡 | 想用独立通行层时，把「通行层」指到这一层 |
| 2… | 随便 | 区域 / 密度 / 高度 … | 任何声明了 `sourceGrid = 2` 的规则集 |

三件事把多层串起来：

1. **`MapTileSet.extraGrids`** 定义「有哪些层、每层有哪些值」（数据侧命名与语义）；
2. **`MapAsset.extraGrids`** 存「每层每格是什么」（数据本体，与定义一一对应）；
3. **`MapAutoRuleSet.sourceGrid`** 决定「这一层的规则看哪份数据」。

规则本身**不知道「网格」这个概念**——它只是拿一个 `CellAt` 委托求值。
所以同一条规则写法，作用在地形层还是通行层，只取决于传进去哪一层的 reader。

> 编辑器的调色板顶部有「编辑网格」下拉。切到哪一层，画笔就落哪一层，
> 其余层在画布上当底色。图层多了也不会看成一团糊。

> **第 0 层是特例字段而不是数组第 0 项**：`materials` 与 `MapAsset.cells` 是初版就有的序列化字段，
> 挪进列表会让已配好的资产数据作废。所以第 0 层保留原名，其余层走 `extraGrids`，
> 对外只有一套 `GridXxx(int grid, …)` 访问器，用起来没有特例感。

## 四、可行走（河流挡路、花草能踩）

**写在值上，不写在地图上**：每层值表里每条都有 `walkable` 勾选。调色板每行右侧的「可走」就是它。

**但只有一层算数**：`MapTileSet.walkableGridIndex` 指定哪一层负责通行判断，默认 0（地形层）。
想让「河挡路」由独立的通行层控制，就在右侧「网格」区把「通行层」指到那一层——
此时地形层的 `walkable` 不再参与判断。

> 调色板里勾了却不生效？看那个值行左边有没有**橙色小点**：有就说明当前编辑的层不是通行层，
> 勾了也不会被读。这不是 bug，是「一个字节只能表达一件事」的必然结果。

派生规则：

| 位置 | 结果 |
| --- | --- |
| 通行层格子不可走 | `MapView.IsWalkable(x,y)` = false |
| 地图外 / 空格 / 未加载 | **一律 false**（地图边界不该被走出去） |
| 碰撞体 | 只由勾了「生成碰撞」的**那一个**规则集生成，且**只给不可走的格子**挂 `TilemapCollider2D` |

> 为什么只该有一层勾「生成碰撞」：多层都开会给同一格叠出多个碰撞体，物理上互相打架。
> 为什么同一张 Sprite 要造两份 Tile：`Tile.colliderType` 是**资产属性**不是实例属性，
> 想让同一张图一处挡一处不挡，只能造两个 Tile 资产。

## 五、怎么画

工具栏：**画笔 / 擦除 / 填充 / 矩形 / 道具**，笔刷 1..9 格，缩放 0.35×..3×。
左侧调色板顶部是「编辑网格」下拉——**所有绘制只落当前这一层**。

| 操作 | 效果 |
| --- | --- |
| 左键拖 | 涂当前值（Bresenham 插值，快速拖动不会断成一串点） |
| 右键拖 | 擦成空（只擦当前层，别层不受影响） |
| 填充 | 洪水填充当前层的同值连通区 |
| 矩形 | 拖出范围，**松手才落地** |
| 道具 | 左键放 / 右键删，**按占地矩形**（多格物件点到任意一格就能整个删掉） |
| Esc | 取消拖动中的矩形 |
| 工具栏「只看层」 | 只渲染当前**规则层**（瓦片层），调规则时用 |
| 调色板「＋ / －」 | 给当前网格加一个值 / 删掉末尾的值 |

### 值只能往后加、只能删末尾

值下标直接写进 Blob。**在中间插入或删除一个值，会让它后面所有值的下标整体平移**，
旧地图就会变成一张错位但「看起来正常」的乱图——这种错最难查。
所以编辑器只允许追加、只允许删末尾；真要重排就得重配规则并重导地图。

### 道具的占地（footprint）

道具在瓦片集里定义 `width × height`（锚点在**左下角**），画布按整块矩形画、锚点那格加深色。
占地不可重叠：放新的之前会先删掉重叠的旧道具。

`MapPropDef.prefab` 只是一个引用位，**框架不会自动实例化它**——生成交给使用方的
`MapView` 子类或另写一个 spawn 系统（道具摆放的时机、生命周期、对象池都跟玩法强相关）。

### 拖预览期间不写数据

矩形按住拖时，编辑器只维护一份 `_preview` 网格副本（**只复制当前那一层**）：
画布渲染、规则求值**全部读这份副本**，资产本身一格都没动。
所以「看到的就是最终效果」和「数据没被动过」同时成立，拖出画布或按 Esc 直接放弃。

### 画布永远是运行期的样子

画布渲染直接调 `MapAutoRules.Evaluate`，和 `MapView` 加载走**同一条路径**。
不存在「编辑器画色块、进游戏才拼边」的两套表现：规则调对了画布就对，调错了画布立刻错。

渲染分三遍：先铺第 0 层值底色，再叠当前编辑层的半透明色标，最后往上叠各层瓦片。
所以「瓦片没配图」（露出底色）和「规则没命中」（露出更深的空底色）是两种不同的视觉，不会混。

## 六、规则怎么写

右侧面板自上而下：**瓦片池 → 规则集 → 规则组 → 规则列表 → 选中规则 → 过渡向导**。

每条规则集有两件事要说清楚：**名字**、**读哪一层**（`sourceGrid`）、**是否生成碰撞**。

### 6.1 3×3 图案编辑器

选中一条规则后，左键点格子往后循环、右键往前循环：
**通配 → 空 → 该层值 1 → 值 2 …** → 回到通配。

三个快捷按钮：

| 按钮 | 作用 |
| --- | --- |
| 中心 = 当前值 | 最常用的起点（取该规则集读的那一层的当前选中值） |
| 全清为通配 | 从零开始画 |
| 四边 = 中心 | 「一片连续区域」的底色兜底瓦片 |

### 6.2 优先级与兜底

**组按列表顺序求值，组内规则也按顺序；靠前的先命中。** 所以典型写法是：

1. 前面：具体规则（过渡、内角、特殊形状）；
2. 后面：兜底规则（`中心=草，其余全通配 → 草瓦片`）。

兜底规则**一定要有**，否则规则没覆盖到的格子这层就是空的。

两个排序按钮省掉手工拖拽：

| 按钮 | 位置 | 作用 |
| --- | --- | --- |
| 按特化度排序 | 规则列表右上 | 把当前组内规则按「约束位数」降序重排 |
| 排序本层 | 规则集那一行 | 对该层所有组各排一遍（**不动组顺序**） |

> 为什么不动组顺序：组顺序本身是「一套过渡压另一套」的语义，
> 打乱它会把「先铺过渡、再铺底色」这种依赖关系破坏掉。

> 排序用的是**插入排序**而不是 `List.Sort`：后者不稳定，同分规则的相对顺序会随机器变，
> 那就意味着「同一份配置在不同机器上画面可能不同」。

### 6.3 命中概率

每条规则有 `chance`（0..1），默认 1。小于 1 时按**格坐标散列**判定——

> 不是 `Random`。同一格每次加载、每台机器、每次回放都得到同一结论。
> 用随机数抖动会在联机/回放里表现为「两边地面花纹不一样」，那种 bug 极难查。

判定失败按「未命中」继续试后面的规则。种子取自图案内容，调换规则顺序不会让整张地图的花纹重排。

### 6.4 候选多张瓦片

一条规则可以挂多张候选瓦片（点瓦片池横条切换）。
命中时按格坐标散列稳定挑一张——同样是散列不是随机，用来做「同一片草地有 3 种小花」这类变化。

### 6.5 瓦片池与「去空槽」

「＋选中」把 Project 窗口选中的 Sprite 加进池；「去空槽」会压缩池并**同步重映射所有规则里的下标**，
所以它不会把地图图案改掉。但**手动删中间的某一项不会重映射**（那就是换图了，是有意为之）。

## 七、怎么导、怎么在游戏里加载

### 7.1 导出 Blob

菜单 `HYC Framework/Map/Export Blob`（或窗口右侧按钮）。

`Assets/StreamingAssets/Map/<mapId>.blob`，只写：尺寸、`GridCount`、**扁平的各层值**
（第 g 层占 `[g·W·H, (g+1)·W·H)`）、道具落点、值层指纹。

**铺哪张瓦片、有几层规则集、规则怎么配，一律不进 Blob。**
所以换美术、改规则、加规则层，都不用重导地图。

指纹（FNV-1a over **所有层名 + 所有值 key**）用来兜「有人在中途插入/删除一个值或一层」——
那会让所有索引整体平移，旧地图变成一张错位但「看起来正常」的乱图。加载时比对不上直接报错。
瓦片与规则**不进指纹**：换美术、改规则都不该逼着重导地图，那正是这套设计想避免的。

> ⚠️ **Blob v2 与 v1 不兼容**：`BlobVersion` 从 1 升到 2（加了 `GridCount`、`Cells` 改扁平多层）。
> 旧版本导出的 `.blob` **读不出来**，会直接报版本不符。升级后每张地图都要重导一次。
> 这是有意的：让旧文件读失败，比让它被当成 v2 解析出一张乱七八糟的图要好得多。

### 7.2 导出装载器 prefab

菜单 `HYC Framework/Map/Export Prefab`。

产出的 prefab 是**装载器**，不是「把几万格烘成 Tilemap」的静态物件：
只挂一个配好 `mapId` / 瓦片集 / 格边长的 `MapView`，运行时 `Start` 读 Blob 建层。

> 为什么不烘：烘进去要给每张瓦片建 Tile 资产（瓦片池 × 图层数的量级），地图一改就得跟着重建；
> 而且烘进去的数据无法复用，两张只差几格的地图会各存一份完整副本。

### 7.3 运行期

```csharp
// 场景里那个 MapView 会按 loadOnStart 自动读 blob 并建层
// 想手动控制就自己调：
mapView.Load(mapId);          // 读 blob + 校验指纹 + 建层，返回是否成功
mapView.Load();               // 用组件上序列化的 mapId
```

自己管 blob 时（比如走 Addressables）：

```csharp
if (MapBlobLoader.TryLoad(mapId, out var blob))
{
    if (!MapBlobLoader.Validate(blob, tileSet, out string error))
        Debug.LogError(error);   // 多半是材质表被改过，指纹不符
    // blob 交给 MapView 的那条路就是 Load(mapId) 内部做的事
}
```

查询接口：

```csharp
byte cell   = mapView.GetCell(x, y);            // 0 = 空，n = 第 0 层的值 n-1
byte pass   = mapView.GetCell(1, x, y);         // 第 1 层（通行层）同格的值
var mat     = mapView.MaterialAt(x, y);         // 第 0 层的值定义（可能为 null）
var val     = mapView.ValueAt(1, x, y);         // 任意层的值定义
bool walk   = mapView.IsWalkable(x, y);         // 读 tileSet.WalkableGrid，地图外/空格/未加载 = false
var layers  = mapView.Layers;                   // Layers[i] 恒对应 ruleSets[i]，空层也建
bool ready  = mapView.IsLoaded;
```

## 八、刻意不做的事

| 不做 | 理由 |
| --- | --- |
| **运行时算边缘** | 边缘是**加载时**算一次（`MapView.Build` 的逐格求值），不是每帧算。所以它不占运行开销 |
| **湿沙 / 湿润扩散子系统** | 「湿沙」不是算法，就是沙地与水这对材质之间的过渡瓦片。做成 BFS 距离场等于把美术问题变成了模拟问题 |
| **把派生量写进 Blob** | 瓦片下标、层结构都是派生量，写进去就锁死了瓦片集，换套美术得把全部地图重导一遍 |
| **随机抖动** | 一律坐标散列。帧同步/回放不能容忍随机差异 |
| **固定 16/47 查表** | 规则是它的超集。16/47 能表达的都是规则的特例，反过来不成立 |
| **把「通行」硬塞进地形值** | 一个字节只能表达一件事。地形种类一旦为通行服务而膨胀，「浅水可走、深水不可走」这种需求就再也表达不了 |
| **自动实例化 `MapPropDef.prefab`** | 道具的生成时机、生命周期、对象池都跟玩法强相关，框架只提供落点数据 |

## 九、排错

| 现象 | 先查什么 |
| --- | --- |
| 某格完全不铺 | 光标信息面板看该层是否「不铺」：规则没命中 → 有没有兜底规则？组是不是被停用了？ |
| 过渡瓦片不出现 | 过渡组是不是在底色组**后面**？（必须在最前面）A/B 值选对了吗？ |
| 三种值交界处没瓦片 | 向导生成的 16 条要求**四条边都是 A 或 B**。第三种值邻居会让它全不命中 → 在过渡组里补一条带对角/第三值约束的规则 |
| 整层都不见了 | 该规则集的组全部 `active=false`，或者「只看层」定在了别的层，或者「读哪一层」指到了没数据的层 |
| 调色板勾了「可走」却不生效 | 当前编辑的层不是「通行层」（值行左边有橙色小点）→ 到右侧「网格」把通行层指过来 |
| 一进游戏就报指纹不符 | 值层或值的顺序被改过（增删/换序/改名）→ 重导 Blob |
| 一进游戏就报版本不符 | Blob v2 不兼容 v1 → 重导 Blob |
| 某些格子不能走却是空的 | `IsWalkable` 对空格返回 false（地图边界不该被走出去）。要可走的空地请铺一种 walkable 值 |
| 道具放下去没反应 | 占地越界（`CanPlaceProp` 为 false）。多格物件锚点在**左下角**，靠近上/右边界时要往回挪 |
| 画布和游戏长得不一样 | 画布求值的就是运行期那份代码，不一样只可能是瓦片池/规则没保存（`Ctrl+S`） |
